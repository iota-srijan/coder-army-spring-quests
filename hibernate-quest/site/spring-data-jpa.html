Declare an interface. Spring writes the repository.

Every repository repeats the same save / find / count / delete code; only the entity type and id type change. Spring Data JPA captures that as JpaRepository<Student, Long>, builds the implementation at runtime, turns method names into queries, and adds sorting and pagination. Underneath it's still EntityManager and Hibernate.

Basic · where it sits

One more layer on top

flowchart TB
  S[Application service] --> R[Spring Data JPA repository]
  R --> E[JPA EntityManager]
  E --> H[Hibernate]
  H --> J[JDBC driver]
  J --> D[(Relational database)]

JPA + Hibernate removed SQL, binding and mapping (entityManager.find(Student.class, id)). But you still wrote a repository class per entity: StudentRepository, DepartmentRepository, CourseRepository… all doing save, findById, findAll, existsById, count, delete.

Only the entity type and id type change, so the idea becomes generic: Repository<EntityType, IdType>. That's the foundation of Spring Data, an umbrella with modules for JPA, JDBC, MongoDB, Redis, Elasticsearch, Cassandra, Neo4j.

@Repository
public class StudentRepository {
    @PersistenceContext private EntityManager entityManager;
    public void save(Student s)          { entityManager.persist(s); }
    public Student findById(Long id)     { return entityManager.find(Student.class, id); }
    public void delete(Student s)        { entityManager.remove(s); }
}   // ...and the same again for every entity
public interface StudentRepository extends JpaRepository<Student, Long> { }
// no implementation class, no @Repository needed; Boot scans the base package

studentRepository.save(student);
studentRepository.findById(id);      // Optional<Student>
studentRepository.findAll();
studentRepository.deleteById(id);

What Spring Data JPA does not remove: understanding entity mapping, transactions, managed/detached states, lazy loading and fetching, SQL performance, indexes and constraints, and N+1. It reduces boilerplate, not the need for sound persistence design.

Core · internals

Who answers each call?

new StudentRepository() doesn't compile: it's an interface. At startup Spring Data creates a repository proxy implementing it. The proxy classifies each call and routes it. SimpleJpaRepository is the standard base implementation (it holds an EntityManager and entity information).

Core · JpaRepository methods

save() means "make this persistent", not "INSERT"

Spring Data decides if the entity is new (by its id or version property, or Persistable). New → persist(). Not new → merge(), which returns a different, managed instance. Always use the return value.

Pick a case.
MethodWhat to remember
saveAll(list)Calls save() per entity. Not one multi-row INSERT; JDBC batching is separate config.
findById(id)Optional<T>; delegates to EntityManager.find(), so the context is checked first.
findAll()Loads everything. Fine for small tables, dangerous for big ones.
existsById(id)An existence query (count or equivalent), not a full load.
count()SELECT COUNT(*) FROM students
delete / deleteByIdEnds at a managed entity; detached ones may be merged/loaded first.
deleteAll()May process entities one by one. Batch methods (deleteAllInBatch) behave differently around cascades, callbacks, context.
flush() / saveAndFlush()Send SQL now (not commit). Use to catch a constraint violation early; not for every save.
getReferenceById(id)A JPA-specific operation in JpaRepository.

You don't need save() to update a managed entity

@Transactional
public void renameStudent(Long id, String newName) {
    Student student = studentRepository.findById(id).orElseThrow();   // managed
    student.setName(newName);                                         // dirty checking → UPDATE at flush
    // studentRepository.save(student);   ← redundant (some teams keep it for consistency)
}
Core · query derivation

Type a method name, get the query

Spring Data parses the name into a subject (findBy, existsBy, countBy, deleteBy, findTop5By…) and a predicate (properties + keywords). Default lookup: use a declared query if there is one, otherwise derive from the name. Entity: Student { name, email, age, active, admissionDate, department → Department { name } }.


  

  
KeywordExampleMeaning

    
(none) / And / OrfindByNameAndAge= ; both ; either

    
GreaterThan / LessThan / BetweenfindByAgeBetween(min, max)> ; < ; inclusive range

    
Like / Containing / StartingWith / EndingWithfindByNameContaining("har")caller's pattern ; %v% ; v% ; %v

    
In / NotInfindByAgeIn(Collection)in / not in a collection

Like vs Containing: with Like you pass "%har%"; with Containing you pass "har" and Spring adds the %. Top without OrderBy has no reliable meaning: the database has no natural row order. Long names like findTop10ByNameContainingIgnoreCaseAndAgeGreaterThanAndActiveTrue… are a sign to switch to @Query, specifications, Query by Example, Querydsl or a custom implementation.

Named parameters (:email + @Param("email")) read better than positional ones (?1, ?2, one-based). Joins follow the mapped relationship: JOIN s.department d, never s.department_id = d.id. Path navigation s.department.name is an implicit join; use an explicit join when you need an alias, several conditions on it, a join type, or to select from both.

  Advanced · native SQL
  
When JPQL isn't enough

  
Use native SQL for database-specific functions or syntax, CTEs and advanced SQL, existing SQL that's awkward in JPQL, or precise control. The cost: you're coupled to the schema and maybe the vendor.

  
@Query(value = """
        SELECT * FROM students WHERE email = :email
        """, nativeQuery = true)                         // table + column names now
Optional<Student> findByEmailUsingNativeQuery(@Param("email") String email);

@NativeQuery("""
        SELECT * FROM students WHERE age >= ?1 AND active = ?2
        """)                                             // recent composed form
List<Student> findStudentsUsingNativeQuery(Integer minimumAge, Boolean active);






  Advanced · sorting
  
Order is part of query design

  
Without ORDER BY the database guarantees no meaningful order. Sort uses entity property names (admissionDate), ascending by default, and must not be null (use Sort.unsorted()). Simulate GET /students?sortBy=…&direction=… with an allowlist.

  

    

    

  






  Advanced · pagination
  
Ask for a window, not the whole table

  
findAll() on two million rows hurts everywhere: DB reads, network, entity objects, persistence-context memory, JSON size. A Pageable (usually PageRequest.of(page, size, sort)) asks for one window. Pages are zero-based; offset = page × size. Page number must be ≥ 0, size > 0; cap size at the API boundary.

  

    

    

    

  

  
Count queries

  
10 rows of content can't tell you whether there are 11 or 10 million in total. For totalElements/totalPages, a Page usually needs a second COUNT query. Spring derives it for simple methods. For complex JPQL (joins, grouping, projections, fetch joins, native SQL), give countQuery: same filters, no ORDER BY, no fetching.

  
@Query(value = """
        SELECT s FROM Student s JOIN s.department d
        WHERE s.active = true AND d.name = :departmentName
        """,
       countQuery = """
        SELECT COUNT(s) FROM Student s JOIN s.department d
        WHERE s.active = true AND d.name = :departmentName
        """)
Page<Student> findActiveStudentsByDepartment(@Param("departmentName") String departmentName, Pageable pageable);

  The gotcha
  

    
Ignoring what save() returns

    
For a detached entity, save() calls merge(), which returns a new managed instance. The object you passed stays detached.

    

      
✗ Later change is lost
studentRepository.save(detachedStudent);
detachedStudent.setAge(25);   // not tracked

      
✓ Keep the managed instance
Student managed = studentRepository.save(detachedStudent);
managed.setAge(25);           // dirty-checked

  • findTop5By… without OrderBy returns an arbitrary five.

  • Raw client input in Sort: validate against an allowlist.
    • 
      
  • Paging on a non-unique sort can shuffle rows between pages: add id as a tie-breaker.

  Recall
  
Answer out loud before opening

  
1. How can an interface be injected and called?
Spring Data creates a runtime proxy implementing it; standard methods route to SimpleJpaRepository, which uses EntityManager.

  
2. What does save() do for a new vs existing entity?
New (null id / version) → persist. Otherwise → merge, returning a managed instance.

  
3. Write the JPQL for findByAgeGreaterThanAndActiveTrue(Integer age).
SELECT s FROM Student s WHERE s.age > ?1 AND s.active = true

  
4. Like vs Containing?
Like: the caller supplies %. Containing: Spring wraps the value as %value%.

  
5. Predict: page 2, size 10. Offset?
20. Records 21–30.

  
6. 45 rows, size 20: how many pages and how many on the last?
3 pages; the last has 5.

  
7. When do you give an explicit countQuery?
For complex content queries (joins, grouping, projections, fetch joins, native SQL). Same filters, no ordering/fetching.

  
8. Page vs Slice in one line?
Page adds totals (usually needs a count query); Slice only knows if there's a next chunk.
