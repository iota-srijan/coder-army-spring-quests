Objects in Java. Rows in MySQL. Hibernate translates.

Java thinks in classes, objects and references. A database thinks in tables, rows and foreign keys. With Spring JDBC you translate between them by hand, every time. An ORM lets you write the translation once, as annotations, and reuses it for every insert, select, update and delete.

The analogy

A translator with a dictionary

You speak Hindi, the shopkeeper speaks only Tamil. Without help, you'd look up every word yourself, every single time you shop. That's Spring JDBC: you write each SQL string, put each value in the right slot and copy each column back into a field.

Now hire a translator and hand them a dictionary once: "my name is your student_name". From then on you just talk; the translator converts both ways. The dictionary is your mapping (annotations), the translator is Hibernate.

Basic · the problem

Same data, different shape

This gap is called the object-relational impedance mismatch. Java can't drop an object into MySQL; it must be turned into SQL-compatible values first.

Java understands

Classes · objects · references · inheritance · encapsulation · collections · object identity · method behaviour

The database understands

Tables · rows · columns · primary keys · foreign keys · constraints · joins · SQL data types

Break it: the parameter-order trap

With jdbcTemplate.update(sql, …) you pass values in the order of the ? marks. Swap two and Java still compiles. Drag nothing: just click two arguments to swap them and see what gets saved.

UPDATE students SET name = ?, email = ?, age = ? WHERE id = ?

And the reverse direction is manual too: a RowMapper copies resultSet.getString("name") into setName(…), one column at a time. Multiply by hundreds of entities and relationships and the translation code grows fast.

Basic · the idea

ORM: write the mapping once

Object-Relational Mapping defines how each Java thing corresponds to a database thing. Click a line on the left to see where it lands on the right.

Click a line of the class.

Knows which class goes to which table, which field to which column.

2SQL generation

Writes INSERT/SELECT/UPDATE/DELETE from entity operations.

3Parameter binding

Pulls values out of the entity and binds them. No order mistakes.

4Result-set mapping

Turns rows back into entity objects. No RowMapper.

5Relationships

References and collections become foreign keys and join tables.

First-level cache (always) and optional second-level cache.

7Transactions

Coordinates entity changes with database transactions.

Mapping table: class → table, object → row, field → column, reference → foreign key, collection → related rows.

Core · who's who

JPA is the interface. Hibernate is the implementation.

JPA originally meant Java Persistence API; today it's named Jakarta Persistence. It defines contracts like @Entity, @Id, EntityManager, EntityManagerFactory and PersistenceContext in jakarta.persistence.*. A specification does no work by itself.

Hibernate implements it. When you import jakarta.persistence.EntityManager, the interface is JPA but the object at runtime is Hibernate's. Same idea as List (interface) and ArrayList (implementation). Other providers: EclipseLink, OpenJPA. Spring Boot's JPA starter brings Hibernate, Spring Data JPA and Spring ORM.

Core · Spring Boot setup

Two dependencies, a few properties

Add Spring Data JPA (spring-boot-starter-data-jpa) and the MySQL driver. We use the starter for config but don't use JpaRepository yet, because it would hide the operations we want to see. Create the database first: CREATE DATABASE student_db;

spring.datasource.url=jdbc:mysql://localhost:3306/student_db
spring.datasource.username=root
spring.datasource.password=your_password

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

Boot builds a DataSource from spring.datasource.*; it supplies JDBC connections to Hibernate. show-sql prints the SQL Hibernate writes, format_sql makes it readable.

Core · first entity, first CRUD

persist, find, change a field, remove

@Entity                         // instances of this class can be persisted
@Table(name = "students")       // ...into this table
public class Student {
    @Id                                                   // primary key
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // MySQL AUTO_INCREMENT fills it
    private Long id;
    private String name;
    private String email;
    private Integer age;

    protected Student() { }      // JPA needs a no-arg constructor
    public Student(String name, String email, Integer age) { ... }
}
@Repository
public class StudentPersistenceRepository {
    @PersistenceContext
    private EntityManager entityManager;   // the JPA interface to Hibernate

    public void persist(Student s)      { entityManager.persist(s); }
    public Student findById(Long id)    { return entityManager.find(Student.class, id); }
    public void remove(Student s)       { entityManager.remove(s); }
}
@Transactional
public void updateStudent(Long id, String newName) {
    Student student = repository.findById(id);
    if (student == null) throw new IllegalArgumentException("Student not found: " + id);
    student.setName(newName);
    // no entityManager.update(...), no repository.save(...)
}

  Advanced · AttributeConverter
  
Database says Y/N, Java says Boolean

  
@Converter
public class BooleanToYesNoConverter implements AttributeConverter<Boolean, String> {
    public String convertToDatabaseColumn(Boolean attribute) {     // Java → DB
        if (attribute == null) return null;
        return attribute ? "Y" : "N";
    }
    public Boolean convertToEntityAttribute(String databaseValue) {  // DB → Java
        if (databaseValue == null) return null;
        return "Y".equals(databaseValue);
    }
}
// in Student:
@Convert(converter = BooleanToYesNoConverter.class)
private Boolean active;

  Advanced · value types
  
@Embeddable: an address lives inside the student row

  

    
A student has its own identity; it keeps existing when its address changes. An address usually has no identity of its own: it's part of the student. That makes it a value type, mapped with @Embeddable (no @Id) and used with @Embedded.

    
There's no address table by default. The object tree is flattened into the student's row. Add a second address and the columns collide, until you rename them with @AttributeOverride.

  

  

    

    

    

  

  
Why bother instead of four loose fields? The entity stops being a bag of unrelated strings; the Java model becomes more expressive and the group is reusable.






  Advanced · collections of values
  
@ElementCollection: a set that needs its own table

  
A Set<String> skills can't fit in one column, so it's stored in a collection table. The rows aren't entities: there's no find(Skill.class, id). Each value belongs to its owning student.

  
@ElementCollection
@CollectionTable(name = "student_skills", joinColumns = @JoinColumn(name = "student_id"))
@Column(name = "skill")
private Set<String> skills = new HashSet<>();

@ElementCollection        // works with embeddables too
@CollectionTable(name = "student_phone_numbers", joinColumns = @JoinColumn(name = "student_id"))
private Set<PhoneNumber> phoneNumbers = new HashSet<>();   // → student_id, country_code, number

  

    

    

  






  Advanced · modelling decision
  
Entity or embedded value?

  
Use an entity when the thing has independent identity: shared by many, queried on its own, updated on its own, referenced by an id, with its own lifecycle. Use a value when it only exists as part of its owner.

  The gotcha
  

    
Two addresses, one set of column names

    
Embedding the same @Embeddable twice gives both copies the columns address_line, city, state, postal_code. Hibernate can't map two fields to one column.

    

      
✗ Conflicting mappings
@Embedded private Address currentAddress;
@Embedded private Address permanentAddress;
// both want column "city"

      
✓ Renamed per location
@Embedded
@AttributeOverrides({
  @AttributeOverride(name = "city",
    column = @Column(name = "current_city")),
  /* addressLine, state, postalCode too */ })
private Address currentAddress;

    

    
    
      
  • name in @AttributeOverride is the Java field (postalCode), not the old column (postal_code).
    • 
      
  • ddl-auto=create drops and recreates the schema at start: existing data is lost. create-drop also drops it at shutdown.
    • 
      
  • validate never fixes anything; it only checks the schema matches.
    • 
      
  • Updating a loaded entity needs no update() call. JPA doesn't even have EntityManager.update().

  Recall
  
Answer out loud before opening

  
1. Why can't Java save an object directly into MySQL?
The database only understands tables, rows, columns and SQL types. The object must first be translated into SQL-compatible values: the impedance mismatch.

  
2. What does Spring JDBC still leave to you?
Writing SQL for every operation, binding values in the right ? order, and mapping rows back to objects with a RowMapper.

  
3. JPA vs Hibernate in one sentence each.
JPA (Jakarta Persistence) is the specification: interfaces and annotations. Hibernate is a provider that implements it and does the actual ORM work above JDBC.

  
4. Predict: ddl-auto=create, table has 3 rows, app restarts. How many rows?
0. create drops and recreates the mapped schema at startup.

  
5. What's precision and scale of 123.456?
Precision 6 (all digits), scale 3 (after the point): @Column(precision = 6, scale = 3).

  
6. Where does an @Embedded Address get stored?
As extra columns in the owner's table (flattened). No separate table, no @Id.

  
7. Where does an @ElementCollection Set<String> get stored?
In a separate collection table (e.g. student_skills with student_id, skill). Its rows are not entities.

  
8. What happens to a @Transient field on save?
Nothing. Hibernate ignores it; there's no column for it.
