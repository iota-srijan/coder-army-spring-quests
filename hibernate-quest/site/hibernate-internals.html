Hibernate doesn't just write SQL. It keeps a workbench.

Inside a transaction, Hibernate keeps an in-memory workspace called the persistence context. It tracks the objects you load or create, notices what you change, and sends the SQL at the right moment. Once that clicks, "why did this UPDATE happen?" and "why didn't my change save?" stop being mysteries.

Core · the workspace

What find() really does

The persistence context is keyed by (entity type, id). find() looks there first. On a miss it runs a SELECT, builds the object, puts it on the bench and starts managing it. The context gives you: identity, lifecycle state, automatic change detection, first-level cache, write-behind and synchronization.

EntityManager is not just "a query runner". Every method touches the entity, the context, or the sync between context and database: persist find remove flush detach clear refresh.

Core · Spring injection

One repository, many requests, many contexts

Repositories are singletons, used by many threads at once. A real EntityManager isn't thread-safe. So @PersistenceContext injects a shared proxy that routes each call to the EntityManager of the current transaction.

@Repository
public class StudentRepository {
    @PersistenceContext
    private EntityManager entityManager;   // actually a proxy, stable for the bean's life
}
Fire requests A and B. Same repository bean, same proxy, different real EntityManagers.
Core · transactions

All or nothing

A bank transfer is two UPDATEs. If the second fails after the first succeeded, money vanishes. A transaction makes them one unit: COMMIT both, or ROLLBACK both. The span between begin and finish is the transaction boundary. A unit of work is every persistence step one business operation needs (load, check rules, modify, detect, generate SQL, run, commit).

BEGIN;
UPDATE students SET email = 'new@email.com' WHERE id = 1;
COMMIT;
Session session = sessionFactory.openSession();
Transaction transaction = session.beginTransaction();
try {
    session.persist(student);
    transaction.commit();
} catch (Exception exception) {
    transaction.rollback();
    throw exception;
} finally {
    session.close();
}
@Transactional      // begin → run → flush → commit, or rollback on exception
public void createStudent(Student student) {
    entityManager.persist(student);
}

By default Spring rolls back on unchecked exceptions (RuntimeException, Error). For checked ones, configure rollbackFor.

Core · how @Transactional works

A proxy stands in front of your service

Spring wraps the service in an AOP proxy. The proxy's TransactionInterceptor starts (or joins) a transaction, calls your method, then commits or rolls back. A call from one method to another on the same object skips the proxy: the self-invocation limitation.

Why transactions belong in the service

@Transactional
public void enrollStudent(Long studentId, Long courseId) {
    Student student = studentRepository.findById(studentId);
    Course course = courseRepository.findById(courseId);
    enrollmentRepository.create(student, course);
    paymentRepository.recordPayment(student, course);   // if this fails, enrollment must roll back too
}

Repository methods do one persistence action. The service method is the whole use case, so it decides what succeeds or fails together. Separate repository-level transactions could commit the enrollment and then fail the payment.

Core · identity map

One row, one object (per context)

Within one persistence context, a given (type, id) is represented by one managed Java object. So two find(Student.class, 1L) calls return the same reference: first == second. Without this rule, two objects for one row could hold conflicting values in the same unit of work.

Student first  = entityManager.find(Student.class, 1L);   // SELECT
Student second = entityManager.find(Student.class, 1L);   // no SELECT
first == second;              // true (same context)
entityManager.contains(first) // true; after detach(first) → false
Core · dirty checking

No update() method, still an UPDATE

Dirty just means "current state differs from the snapshot". A setter doesn't run SQL. At flush, Hibernate compares each managed entity with its snapshot and generates UPDATEs for the differences. JPA doesn't even define EntityManager.update().

Advanced · flush vs commit

Sending SQL isn't the same as finishing

Flush sends pending SQL inside the current transaction; it can still be rolled back. Commit ends the transaction successfully and makes changes durable. With the default AUTO flush mode, Hibernate flushes before commit and before queries whose results pending changes could affect.

    Transactional write-behind

    Write-through would send SQL after every Java change. Hibernate is write-behind: changes collect in the context and go out at flush. That lets it skip useless work, order statements, group them and use JDBC batching, all still inside the transaction.

    Manual entityManager.flush() is useful to hit a constraint violation early, to sync before later database work, or with clear() in batches.

    Advanced · batch processing

    100,000 inserts without running out of memory

    for (int i = 0; i < 100_000; i++) {

    Advanced · first-level cache

    The bench is also a cache

    The persistence context is the first-level cache: on by default, can't be turned off, belongs to one context (one transaction in Spring), and guarantees identity. It is not application-wide.

    Persistence context
    SELECTs sent: 0
    • find() by primary key can be served from the context. A JPQL/Criteria query still runs SQL; Hibernate then hands back the already-managed instances.
    • The cache can hold stale values if another transaction changes the row. refresh() reloads, and throws away unsynchronized in-memory changes, so use it on purpose.
    • detach(e) affects one entity; clear() every entity. After clear(), first == second is false: first is the old detached object.

    The gotcha

    Using the argument of merge() instead of its return value

    merge() copies the detached object's state into a managed instance and returns that instance. The object you passed in is still detached. Changes made to it after the merge are lost.

    ✗ Change is lost
    entityManager.merge(detached);
detached.setName("Rohan");   // detached: not tracked
    ✓ Use the managed copy
    Student managed = entityManager.merge(detached);
managed.setName("Rohan");    // dirty-checked → UPDATE
    • Changes after detach/clear aren't saved. Dirty checking only sees managed entities.
    • Self-invocation skips @Transactional. this.update() bypasses the proxy.
    • flush() is not durable. A later exception still rolls back what was flushed.
    • Setting the same value (setName("Rahul") when it's already Rahul) normally produces no UPDATE.
    Recall

    Answer out loud before opening

    1. Why does Spring inject a proxy for EntityManager?

    Repositories are singletons shared by threads; a real EntityManager isn't thread-safe. The proxy routes each call to the EntityManager bound to the current transaction.

    2. Name the four lifecycle states and one way into each.

    Transient (new), managed (persist/find), detached (detach/clear/context ends), removed (remove).

    3. Predict: find(1), setName("Rohan"), method returns. Which SQL?

    SELECT at find, then at flush before commit: UPDATE students SET name='Rohan' WHERE id=?.

    4. Predict: find(1), detach, setName("Rohan"), method returns.

    Just the SELECT. The entity is detached, so no dirty checking, no UPDATE.

    5. flush vs commit?

    Flush sends SQL inside the transaction (can roll back). Commit finishes the transaction; changes become durable.

    6. Why flush() and clear() every 100 rows in a batch?

    flush sends the pending inserts; clear detaches them so the context doesn't grow to 100,000 managed objects.

    7. find(1) in methodA and again in a separate @Transactional methodB. How many SELECTs?

    Two. Each transaction has its own persistence context, so its own first-level cache.

    8. Why put @Transactional on the service, not each repository method?

    The service method is the whole business operation; all its repository calls must succeed or fail together.
