The whole topic on one map

The analogy

A restaurant waiter

A table of 10 orders soup. A bad waiter walks to the kitchen and back once per bowl: 1 trip to take the order + 10 trips for soup. A good waiter, knowing everyone wants soup, brings one tray. The first is N+1; the tray is a fetch plan for this use case.

Bread is brought only if someone asks for it: lazy. Bread forced on every table, even those who never eat it: eager. And when the table's bill is cancelled, its side dishes are cancelled too, but not the chef shared by every table: cascade remove is for things that belong only to you.

Core · cascading

Does the operation flow to the children?

A cascade propagates a persistence operation from one entity to another through a mapped relationship. It's off by default, on purpose: related entities don't always share a lifecycle. Cascading is not ownership: OrderItem.order still owns the order_id FK, so use addItem() to set both sides.

@OneToMany(mappedBy = "order", cascade = CascadeType.PERSIST)
private List<OrderItem> items = new ArrayList<>();

public void addItem(OrderItem item) { items.add(item); item.setOrder(this); }

order.addItem(item1); order.addItem(item2);
entityManager.persist(order);   // ≈ persist(order); persist(item1); persist(item2);
cascade =

Ask the right question before adding a cascade: "If this parent is persisted (or removed), should these related objects always be persisted (or removed) with it?"

Core · danger

CascadeType.REMOVE on shared entities

An OrderItem has no meaning without its order, so cascading remove is reasonable. A Course is shared by many students. Remove one student with cascade = REMOVE on @ManyToMany courses and the course disappears for everyone.

Core · reference

The six cascade types

Cascade typePropagated operation
PERSISTPersist new related entities
MERGEMerge state of related detached entities
REMOVERemove related entities
REFRESHReload related entities from the database
DETACHDetach related entities from the persistence context
ALLAll of the above. Only when the child shares the parent's whole lifecycle.
@OneToMany(mappedBy = "order", cascade = { CascadeType.PERSIST, CascadeType.REMOVE })
private List<OrderItem> items;
Core · when to load

A fetch plan, and the defaults

A Student may link to Department, Address, Profile, Courses, Projects, Certificates, Comments… each with more links. Loading everything reachable for one student could load half the database. Hibernate needs a fetch plan: what's needed now, what can wait.

Setting fetch = … on the mapping is a static fetch strategy: the default whenever the entity loads. A fetch join or entity graph can override it per use case.

Pick a relationship annotation.

EAGER is a requirement: the provider must make the data available. LAZY is a hint: the provider is asked to delay, but the spec doesn't force it. Hibernate supports lazy well: lazy persistent collections for to-many, proxies or bytecode enhancement for to-one. Many teams set to-one relationships to LAZY explicitly.

Core · under the hood

A proxy that fills itself on first real use

Lazy loading is useful because use cases differ: a student list needs id + name; a details page adds department and profile; a report adds courses and projects. One big eager graph wastes work for two of the three. The risk: SQL now fires implicitly as code walks relationships. That's how N+1 appears.

Advanced · the N+1 problem

Count the hidden queries

1 query loads the parents, then 1 more per parent when the loop touches a lazy relationship. Change the numbers and the strategy. Notice the first-level cache: once a department is managed, other students reuse it, so the real count can be 1 + distinct departments, not 1 + N. Still a fetch-plan problem.

  Advanced · tempting non-fix
  
Does N+1 mean lazy is bad?

  
No. The problem is knowing you'll use an association for every row and not putting it in the query's fetch plan. Switching the mapping to EAGER isn't reliable: JPA requires the data be available, not that it come from one join. Hibernate may still run secondary selects. And EAGER is global: every other use case pays too.

  
Use caseNeeds department?Mapping EAGERLAZY + per-query graph

    
Student list (id, name)NoLoads departments anywayDoesn't load them

    
Student + department tableYesLoaded, maybe via secondary selectsFetched in that query's plan

    
Count studentsNo——

  
Rule: keep relationships lazy by default; fetch the required graph explicitly for each use case. LAZY sets default timing; the query-level plan sets what an operation needs. Check the generated SQL either way.

  Advanced · the fix
  
@EntityGraph: a fetch plan per repository method

  
public interface StudentRepository extends JpaRepository<Student, Long> {

    @EntityGraph(attributePaths = "department")                 // Student + Department
    List<Student> findAll();

    // several:  attributePaths = { "department", "profile" }
    // nested:   attributePaths = { "department.manager" }      // Student → Department → Manager
}

  
The mapping stays LAZY for everything else; this one method fetches what it knows it needs. Hibernate commonly uses a join, but the graph defines what to fetch, not one guaranteed SQL shape. Be careful with nested graphs and several large collections at once: the joined result grows big and duplicates rows at the SQL level.

  

    

    

    

  






  The gotcha
  

    
"Fixing" N+1 by switching to EAGER

    
It feels like the obvious fix, but it changes every use case globally and still doesn't promise one query.

  Recall
  
Answer out loud before opening

  
1. What does CascadeType.PERSIST on Order.items do?
persist(order) also persists new items reachable through the collection.

  
2. Why delete child rows before the parent?
So the child FK doesn't violate the constraint pointing at a deleted parent.

  
3. Default fetch types for the four annotations?
@OneToMany and @ManyToMany LAZY; @ManyToOne and @OneToOne EAGER.

  
4. Does student.getDepartment() on a lazy proxy run SQL?
Not necessarily; getting the reference doesn't. Reading real state like getName() triggers initialization.

  
5. Predict: 100 students, 3 departments, lazy, loop prints department names. Queries?
Typically 1 + 3 thanks to the first-level cache, though the pattern is still N+1.

  
6. EAGER: requirement or hint? LAZY?
EAGER is a requirement; LAZY is a hint.

  
7. What's the principle for avoiding N+1?
Lazy by default; fetch the needed graph per use case (entity graph / fetch join), and check the SQL.
