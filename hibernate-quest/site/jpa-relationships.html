Java holds references. Databases hold foreign keys.

student.getDepartment() is an object reference. In MySQL the same fact is a number in students.department_id. Relationship mapping tells JPA how to turn one into the other, which side is in charge of that number, and how many can link to how many.

Basic · the problem

A column can't hold an object

Without an ORM you'd store private Long departmentId;. With JPA you keep a real Department reference and Hibernate writes its id into the foreign key. Click a student to follow the reference.

Real models are a graph of connected objects: Student → Department, Order → List<OrderItem>, Employee → manager Employee, User → Profile. These links are relationships (associations).

Basic · navigation

Unidirectional or bidirectional?

These words are about Java navigation, not SQL. Unidirectional: only Student has a department field, so department.getStudents() doesn't exist. Bidirectional: both have fields. It's still one foreign key. And the two fields don't synchronize themselves.

// Unidirectional: Student → Department
class Student    { Department department; }
class Department { }
// Bidirectional: Student ↔ Department
class Student    { Department department; }
class Department { List<Student> students; }
Core · who's in charge

Owning side vs inverse side

When both entities map the same relationship, JPA needs one authority. The owning side is the side JPA reads to decide the foreign-key value. It's not "the parent" or "the more important entity". The inverse side (mappedBy) is a read-only mirror for navigation.

Core · many-to-one

@ManyToOne + @JoinColumn

@Entity
public class Student {
    @Id @GeneratedValue private Long id;
    private String name;

    @ManyToOne                                // many students → one department
    @JoinColumn(name = "department_id")       // the foreign-key column (references departments.id)
    private Department department;
}

If engineering.getId() == 5, then student.setDepartment(engineering) stores department_id = 5. Changing a managed student's department to HR makes dirty checking issue UPDATE students SET department_id = 20 WHERE id = 1: relationship dirty checking.

Core · one-to-many

@OneToMany(mappedBy = "department")

The department's list is an object-side view of rows that already have department_id. No new column. mappedBy names the Java field in Student, not the column.

@Entity
class Department {
    @Id private Long id;
    private String name;

    @OneToMany(mappedBy = "department")          // "the field called department in Student owns this"
    private List<Student> students = new ArrayList<>();
}

Which value goes in mappedBy?

Pick one.

Hibernate does detect changes to a managed collection (collection dirty checking), but detecting a change isn't the same as owning the foreign key. Removing from department.getStudents() alone won't clear department_id; you also need student.setDepartment(null).

Core · keep it consistent

Put the two-sided update in one method

public void addStudent(Student student) {
    students.add(student);           // inverse side (Java navigation)
    student.setDepartment(this);     // owning side (decides the FK)
}
public void removeStudent(Student student) {
    students.remove(student);
    student.setDepartment(null);
}
// usage
engineering.addStudent(rahul);
engineering.removeStudent(rahul);

The helper keeps the in-memory graph consistent and guarantees the owning side is set. Try addStudent in the owning-side lab above.

Advanced · one-to-one

Foreign key + unique constraint

A plain foreign key allows repeats, which is many-to-one. One-to-one needs the FK value to be unique. Try inserting extra profiles for user 1.

@Entity class Profile {                // OWNING side: has the join column
    @Id @GeneratedValue private Long id;
    private String bio;
    @OneToOne(optional = false)
    @JoinColumn(name = "user_id", nullable = false, unique = true)
    private User user;
}
@Entity class User {                   // INVERSE side
    @OneToOne(mappedBy = "user")        // Profile.user
    private Profile profile;
}

Shared primary key with @MapsId

When a profile can't exist without its user, it can reuse the user's id: profiles.id is both the primary key and a foreign key to users.id.

@Entity class Profile {
    @Id private Long id;
    private String bio;
    @OneToOne @MapsId
    @JoinColumn(name = "id")
    private User user;     // user 10 → profile 10
}
Advanced · many-to-many

A join table of pairs

Neither students nor courses can hold the link in one column, so a third table holds pairs: a join / association / junction table with two foreign keys. Click cells to enrol. The (student_id, course_id) unique constraint blocks duplicates.

@ManyToMany                                     // OWNING side: has @JoinTable
@JoinTable(
    name = "student_course",
    joinColumns        = @JoinColumn(name = "student_id"),   // points to the owner (Student)
    inverseJoinColumns = @JoinColumn(name = "course_id"),    // points to the other side
    uniqueConstraints  = @UniqueConstraint(columnNames = {"student_id", "course_id"}))
private Set<Course> courses = new HashSet<>();

// in Course: INVERSE side
@ManyToMany(mappedBy = "courses")
private Set<Student> students = new HashSet<>();

public void addCourse(Course course)    { courses.add(course);    course.getStudents().add(this); }
public void removeCourse(Course course) { courses.remove(course); course.getStudents().remove(this); }
Advanced · Lombok

@Data on a bidirectional entity

@Data generates getters, setters and toString(), equals(), hashCode(). With Student ↔ Department, toString() walks back and forth forever.

  • Recursive navigation → StackOverflowError
  • Unexpected lazy loading
  • Comparing large collections
  • Unstable equality / hash codes for entities

If you do generate toString/equals/hashCode, exclude relationship fields and design entity identity deliberately.

  2. Uni/bidirectional describe Java navigation; bidirectional is still one relationship.
  3. The owning side decides what JPA writes. mappedBy points at a Java field.
  4. Keep both sides in sync; use helper methods.
  5. Setting a reference doesn't persist the referenced entity. Cascading controls lifecycle, not ownership.
The gotcha

Adding only to the mappedBy collection

The list on the inverse side looks like the "parent's" list, so it feels authoritative. It isn't. JPA writes the foreign key from the owning side.

✗ department_id stays NULL
engineering.getStudents().add(rahul);
// rahul.department is still null
✓ Owning side set
engineering.addStudent(rahul);
// students.add(rahul) + rahul.setDepartment(this)
  • mappedBy = "department_id" is wrong: use the field name "department".
  • A FK without unique isn't one-to-one: the DB allows many profiles per user.
  • Setting only the owning side saves correctly but leaves the in-memory list stale for the rest of the transaction.
  • @Data on entities can recurse into StackOverflowError.
Recall

Answer out loud before opening

1. How does a database represent student.department?

A foreign-key column students.department_id referencing departments.id.

2. Is a bidirectional Student ↔ Department two relationships?

No. Two Java navigation paths, one foreign key.

3. Which side owns a bidirectional one-to-many?

The @ManyToOne side with @JoinColumn (Student). Department's list is the inverse side.

4. Predict: only engineering.getStudents().add(rahul), then flush.

No change to department_id; the inverse side doesn't control the FK.

5. What makes one-to-one different from many-to-one in the schema?

The foreign key gets a unique constraint.

6. What do joinColumns and inverseJoinColumns mean?

joinColumns: FK to the owning entity (student_id). inverseJoinColumns: FK to the other entity (course_id).

7. What does @MapsId do?

Uses the associated entity's id as this entity's id: shared primary key.

8. Why avoid @Data on JPA entities?

Generated toString/equals/hashCode can recurse through bidirectional relationships, trigger lazy loads and compare big collections.
